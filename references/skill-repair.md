## 何时使用

用户已有提示词、技能或流程规则，但出现以下信号时，走本路线而不是普通评审：

- 同类失败反复出现，改一两句措辞后仍复发。
- 规则写得很多，但执行时被忽略、跳过或只执行一部分。
- 输出质量退化：结论无证据、格式漂移、缺字段、遇缺失输入就编造。
- 模板或示例本身在反向暗示错误做法。
- 修复后没有可核对的回归证据，只凭“感觉更好”。

普通旧提示词评审仍按 `review-checklist.md`；本路线用于结构性缺陷。

## 归因五类

| 编号 | 归因 | 典型表现 | 要补什么 |
|---|---|---|---|
| a | 规则缺失 | 该防的失败模式没有任何规则覆盖 | 增加一条可执行、可判定的硬约束 |
| b | 规则可被绕过 | 规则是“建议”“尽量”，没有优先级、例外或拒答条件 | 改成必须/禁止，写清冲突时的优先级 |
| c | 缺降级算法 | 输入缺失、工具不可用、结果冲突时没有下一步 | 给出澄清、占位符、停止或降级路径 |
| d | 缺结构闭环 | 直接产出最终答案，没有中间产物或自检门 | 加提纲、清单、JSON、检查点等可观察中间物 |
| e | 模板反向暗示 | 示例、默认模板或字段名诱导错误行为 | 改模板与示例，删除反向暗示 |

归因表至少写：失败样例、对应归因、证据位置、修复动作。不要把“模型不听话”当归因。

## 四件套

1. **硬性结构约束**：必须做什么、禁止做什么、先后顺序、冲突时谁优先；关键处给出拒答或停止条件。
2. **中间产物**：先产出可检查的提纲、表格、JSON 或检查清单，再产出最终答案；中间物要能被人工或程序核对。
3. **降级算法**：缺失输入、工具不可用、结果冲突时，明确是澄清、用占位符、降级输出还是停止；禁止编造。
4. **可数自检门 + 禁用做法**：用可数的检查项（如“3 项必查”）代替“仔细检查”；同时列出明确禁止的做法。

四件套不必全部堆进一份提示词；按归因选择，能解决问题即可。

## 回归要求

- 用真实失败输入做回归，不用凭空编造的样例替代。
- 保留修复前基线；对同一输入比较修复前后的行为，逐条写通过/失败。
- 回归行至少覆盖：原失败样例、一个边界输入、一个缺失输入；高风险任务按 `test-cases.md` 补五类测试。
- 没有实际运行证据时，效果只写“预计”，并说明未运行的原因与影响。
- 修复后再次出现同类失败，回到归因表，不叠加更多口号式规则。

## 交付物

1. 归因表（失败样例 → a–e 归因 → 证据 → 修复动作）。
2. 修复后的完整文件，不只给零散 diff。
3. 章节级改动清单：改了哪一节、为什么、对应哪条归因。
4. 回归结果：基线/修复后、输入、通过标准、实际结果或“预计”。
5. 一句话兜底规则：下一次遇到同类失败时，先检查哪一项。

## 版本与同步

- 修复改变规则结构时升次版本；只改措辞或示例升修订号。
- 同步更新文件头版本、更新日期、修改记录和 README 的目录/说明。
- 不借修复重写技能定位、核心边界或用户未要求改动的部分；历史结论保留时间和适用范围。
